Revised Design: Detect Sleep vs. Tab Switch

The key insight: on desktop/laptop, JS timers keep running during a tab switch — probes still flow. Sleep freezes everything. We can use this to tell them apart.

What actually happens per platform
JS timer behaviour when page is hidden
Scenario JS timers Probes received?
Desktop/laptop — tab switch Keep running Yes — connection is fine
Desktop/laptop — lid close / sleep Frozen No — everything is frozen
Mobile — tab switch Frozen by browser No — JS is frozen
The revised approach: detect on wake, not on hide
How it works

Instead of starting a timer when the page hides, we check on wake:

  1. When page hides: record hiddenAt (wall clock) and probeCountAtHide (probes received so far)
  2. When page shows again: compare current probe count to probeCountAtHide
  3. If probes increased → tab switch on desktop, JS was running → continue
  4. If probes unchanged AND hidden for >30s → JS was frozen (sleep or mobile) → stop

No setTimeout needed. The probe count is the signal.

Outcome by scenario
Scenario Result
Desktop/laptop — tab switch (any duration) Continue — probes flowed during hide
Desktop/laptop — lid closed / sleep >30s Stop on wake — "computer went to sleep" (green)
Mobile — tab switch >30s Stop on return — "Cutie only works when visible" (green)
Mobile — brief tab switch <30s Continue — grace period not exceeded
User clicks Stop while hidden Manual stop wins
Device sleeps while already in another tab Stop on wake — same logic, probes didn't flow
Code changes (still all in webrtc.ts)
  • Two module variables: hiddenAt: number | null, probeCountAtHide: number | null
  • visibilityChangeHandler: on hide → record values; on show → compare and maybe disconnect('sleep')
  • No setTimeout — simpler than before
  • Same listener attach/remove lifecycle as the previous design
